# 项目级成员权限设计

## 目标

将团队成员的项目访问从工作区全局可见改为按项目显式授权，适用于一个工作区内包含多个源码项目的小团队。

## 范围

- 新增项目成员关系和项目内角色。
- 在项目协作页管理现有工作区成员的项目访问。
- 所有项目范围 REST 接口、知识检索和 MCP 项目 Token 统一执行项目权限校验。
- 保留工作区管理员的全局管理能力。

不包含邀请邮件、项目外部用户、跨工作区组织、计费和全局通知中心。

## 权限模型

新表 `project_members` 包含 `project_id`、`user_id`、`role`、`created_at`，并以 `(project_id, user_id)` 唯一约束保证单个成员在项目内只有一个角色。

项目角色沿用现有角色名称，但只在项目范围内解释：

| 角色 | 权限 |
| --- | --- |
| `admin` | 管理项目成员、资料来源、构建、发布、Token 与项目设置。 |
| `member` | 上传资料、发起构建、处理反馈、查看项目知识与活动。 |
| `reader` | 只读查看已发布知识、项目资料与活动。 |

工作区 `admin` 是全局兜底角色：可访问和管理工作区中的任何项目，不必拥有对应的 `project_members` 行。工作区 `member` 和 `reader` 必须拥有项目成员关系才能读取或操作目标项目。

## 数据迁移

迁移创建 `project_members` 和必要索引。现有每个项目均补充其工作区管理员为项目 `admin`，使已部署的项目在迁移后可继续由管理员管理。其他现有工作区成员不自动获得项目访问权限。

创建新项目时，创建者自动加入为项目 `admin`。项目成员只能来自同一工作区的现有成员；跨工作区成员、重复添加和向不存在项目写入均被拒绝。

## 服务端边界

持久化层提供项目成员的列出、添加、更新角色、移除及访问查询接口。应用层将当前“工作区角色校验”拆为两步：先完成会话认证和工作区角色校验，再对请求中的项目 ID 校验项目访问与所需项目角色。

所有接收 `x-devkh-project`、路径项目 ID 或从项目 Token 推导项目 ID 的接口都复用同一授权帮助函数。无权访问时返回 `403 PROJECT_ACCESS_DENIED`；不以权限失败泄露其他项目的资料、快照、构建、发布、Token、反馈或知识内容。

项目 Token 仍绑定单一项目。MCP 请求在 Token 认证后只访问 Token 所属项目，不依赖浏览器会话；项目成员变更不会扩大 Token 的项目范围。

## 界面与 API

项目协作页显示真实项目成员及项目角色，不再展示“团队角色”或暗示全员可访问。项目管理员可在页面中：

- 从工作区现有成员中添加项目成员并指定角色。
- 修改非自身项目成员的角色。
- 移除非自身项目成员。

不能添加不存在于工作区的账号；页面对非项目管理员隐藏管理操作，但服务端校验始终有效。工作区成员页继续管理账号与全局工作区角色，不承担项目访问分配。

## 失败处理与审计

成员操作必须原子完成并写入项目范围审计事件：添加、角色变更和移除均记录操作者、目标成员、项目与变更后的角色。最后一个可管理项目的管理员不可被移除或降级，避免项目失管；工作区管理员不受该限制，因为其保留全局兜底访问。

## 测试与验收

- PostgreSQL 迁移验证表、唯一约束、同工作区外键边界和管理员回填。
- 内存与 PostgreSQL 持久化测试覆盖项目成员 CRUD、重复请求和最后项目管理员保护。
- 路由测试覆盖 `admin`、`member`、`reader`、非项目成员和工作区管理员的允许/拒绝矩阵。
- MCP 与搜索测试验证项目 Token 不跨项目，浏览器会话成员也不能读取未授权项目。
- 前端测试验证项目协作页显示真实项目角色，并仅向项目管理员显示成员管理控件。

验收标准：在同一工作区创建两个项目后，普通成员只可访问被分配的项目；工作区管理员可管理两者；所有知识、构建、发布、资料和 Token 路由都保持这一边界。
